## 阶段 0 · 起点

**需求**：智能体（agent）控制剪映完成视频剪辑。

**原始提问**：怎么样智能体才能控制剪映进行视频剪辑？

**范围逐步明确**：


最后收敛成一句：**要一个能给 agent 用的 MCP + 一份说明文档。**

## 阶段 1 · 路线调研

联网检索后，CapCut/剪映的程序化控制只有这几类方案：

| 方案 | 代表 | 结论 |
|---|---|---|
| 剪贴板/快捷键自动化 | AutoHotkey 脚本 | 只能做固定动作，不可编程 |
| UI 自动化 | pywinauto / UIA | 剪映 11.5 是 QML 渲染，UIA 暴露 0 控件 → **死路** |
| 剪映官方 API | 无公开 API | — |
| **直接改草稿工程文件** | pyJianYingDraft / CapCutAPI | **可行** |
| 逆向引擎 DLL 直接调用 | jy-draftc | 可行但极难 |
| 剪映内置 CLI | lyra-cli（后来才发现） | **最优解** |

**关键发现**：剪映的草稿是**明文 JSON**。

```text
草稿目录/
├── draft_content.json        工程内容 —— 明文
├── draft_meta_info.json      元信息
├── draft_settings            ini
└── draft_virtual_store.json
```

这一步定下了整条路线的地基。

## 阶段 2 · 草稿格式摸清

### 做了什么

1. 在本机剪映草稿目录里挑了一个真实草稿
2. 打开 `draft_content.json` → 内容是 `hFHc6dlGEHDTFtC5…` 乱码
3. 在 `videoeditor.dll` 里找到 `EncryptUtils`：

   ```text
   EncryptUtils::isFileEncrypted
   EncryptUtils::decrypt
   EncryptUtils::encrypt
   ```

4. ctypes 加载 dll → 调 `decrypt` → 拿到 46521 字节明文 → 验证 `encrypt` 往返一致

### 结论

- 剪映**自己生成**的草稿会加密
- 但它**读取**时不需要加密，明文照读
- 所以：**写自己的草稿 = 写明文 JSON**

### 坑

**`GetProcAddress` 返回 0，`GetLastError() = 127`**

手打的 MSVC 装饰名（130~160 字符）差一个字符就失败。
→ 改成从 PE 导出表按原始字节读符号名。`videoeditor.dll` 有 32568 个具名导出。

## 阶段 4 · 逆向引擎 DLL（失败，但留下关键资产）

### 目标

通过 `videoeditor.dll` 直接驱动剪映引擎，绕过草稿文件。

### 参考

`jy-draftc`（MIT 开源）的 Windows 实现，逆推出启动序列：

```text
Server::instance()
  → Server::startup(server, nullptr, injector[64])
  → openSession(server, nullptr, &name)
```

### ABI 定位（11.5.0.14471）

| 符号 | RVA |
|---|---|
| `operator new` | `0x02D8D60C` |
| `vt_request` | `0x0302FB28` |
| `vt_control` | `0x03030060` |
| `restore_draft` | `0x011C41A0` |
| `export_factory` | `0x011B3AC0` |

`JsonApiClient::invokeJsonRequest(ret*, req*)` 内部调 `Server::invoke(server, ret, req, -200)`。

### ReqStruct 布局（推算自 MIT 源码）

| 偏移 | 字段 |
|---|---|
| `+0x00` | vtable |
| `+0x08` | `std::string service`（32 B） |
| `+0x28` | `std::string api`（32 B） |
| `+0x48` | `int32 task_id` |
| `+0x58` | `int32 in_kind` |
| `+0x80` | payload (Pair) |
| `+0x90` | `uint16 bools` |
| 总长 | `0x98`，control block 在 `object-0x10` |

MSVC 内存布局：

```text
std::string   = 32 B  (16 SSO buf + size + capacity)
shared_ptr    = {ptr@+0, ctrl@+8}
ctrl block    = {vtable@+0, uses@+8, weaks@+12}
engine object = _Rep + 0x10
```

### 结果：失败

```text
openSession  →  抛 C++ 异常 0xe06d7363，位置 server.cpp:234
invokeJsonRequest →  access violation reading 0x...FFFF
                    mov rax,[r14] → [obj+0x20] (string capacity)
                    → mov r8,[rcx-8] (析构读 allocator 头)
```

还会 `exit 0xC0000374`（堆损坏）—— 因为 ≥16 字节的 `std::string` 走堆分配，Python 分配的 buffer 引擎释放不了。

→ 超长字符串必须用引擎自己的 `operator new`（`0x02D8D60C`）分配。
→ 改成 `PAD=0x10` 后崩溃点不变。

### 结论

**放弃这条路。** 因为阶段 2 已经证明「写 JSON 就够」，没必要为了"更底层"去对抗一个没有文档的引擎。

> 教训：能达成同样效果的两条路里，选不需要对抗实现的那条。

### 留下的资产

- **PE 导出表解析器**（现在在 `re/engine_api.py`）
- **vcxproj 逆向方法论**
- `jydll.py`（草稿解密，这条路的副产品，现在还在用）

## 阶段 5 · pyJianYingDraft + MCP 落地

### 做了什么

1. `.venv-jianying` 装 `pyJianYingDraft 0.3.0`
2. `src/server.py`：14 个端点，覆盖 建草稿/视频/图片/音频/文本/特效/滤镜/转场/动画/关键帧/音量关键帧/保存/部署/导出
3. `src/mcp_server.py`：零依赖 stdio JSON-RPC，把这些包成 MCP 工具
4. 产出 `docs/02-MCP使用手册.md`

### 关键 API 坑

| 坑 | 正解 |
|---|---|
| `script.tracks` 是 dict | `for name, track in script.tracks.items()` |
| 关键帧时间不能传 `Timerange` | 用 int 微秒 或 `"1.5s"` |
| 主轨首尾相接 | `start` 由 `cursor` 自动推，要留空隙需显式传 |
| 素材必须先注册到 `materials` | 用 `add_*` 方法，别手写 JSON |

### 部署机制

三步，缺一不可：

```text
1. Copy-Item 草稿目录
2. 补 draft_settings + draft_virtual_store.json
3. 在 root_meta_info.json 的 all_draft_store 里注册一条
```

**权限坑**：从 Python subprocess 拉起的 PowerShell 写不进草稿目录（token 受限）。
原生 PowerShell 没问题。→ 后来单独做了 `env/deploy.ps1`。

## 阶段 10 · 宿主校验攻坚（三次弯路）

### 症状

```json
{"err_category":"runtime","err_code":-100015,
 "err_msg":"unauthorized host process","recovery":"upgrade_or_switch_path",
 "severity":"failed"}
```

任何命令都拒绝，**连 `--help` 都拒绝**，`exit=1`。

---

### 弯路 1 · 伪装父进程

**做法**：把 `python.exe` 复制成 `JianyingPro.exe`，用
`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` 让它当父进程。

**结果**：`exit=1` → **`exit=0`，无输出**。

当时以为成功了。

---

### 弯路 2 · 用 Procmon 验证，发现是假突破

**做法**：装 Sysinternals Procmon，抓 `lyra-cli` 的完整系统调用。

**结果**：

```text
总操作 16 条
  lyra-cli.exe      8 次  Read Attributes（打开自己）
  lyra-cli.cmd      8 次  打开 wrapper 脚本
命名管道    0
网络请求    0
共享内存    0
```

**`exit=0` 时它什么都没干。** 不是通过校验后执行，是被骗后走了另一条静默退出分支。

**同时也查清了官方结构**：

```text
Resources\agent_runtime_env\
├── env-manifest.json          只有平台/哈希清单，无环境变量、无 IPC 名
├── bin\lyra-cli.cmd           纯转发：..\..\lyra-cli.exe %*
├── bin\lark-cli.cmd
└── cli\npm-tools\node_modules\@larksuite\cli\bin\lark-cli.exe   (27 MB 飞书 CLI)
```

`jianying-agent-cli.exe` 是另一个官方组件，支持：

```text
draft <fetch-feishu-doc|query-content|plan-patch|validate-patch|apply-patch> --input <json>
```

它的 `lyraCommands` 白名单只放 `edit` / `extract`，走不通搜索。

---

### 弯路 3 · 找字符串引用找不到

**做法**：在 `.rdata` 里定位错误字符串。

```text
lyra-cli.exe         RVA 0x00A43208
lyra_cli_client.dll  RVA 0x0078E9C8
```

**结果**：搜 `lea` 指令 **0 命中**。

**原因**：现代 MSVC 用 **RIP-relative** 编码：

```asm
48 8D 05 <disp32>        ; lea rax, [rip + disp]
; 目标 RVA = 当前 RVA + 7 + disp
```

手工搜 `lea` 助记符搜不到，必须**按机器码模式扫描并回算目标地址**：

```text
REX(48/4C) + 8D + modrm ∈ {05,0D,15,1D,25,2D,35,3D}
```

→ 每个文件各命中 **1 处**。

---

### 正解

反汇编 `lyra-cli.exe` RVA `0x1A3A8` 附近：

```asm
0x1A392  lea  rcx, [rbp-0x60]
0x1A396  call 0x140885310             ; 填两个 bool
0x1A39C  cmp  byte [rbp-0x60], r14b   ; flag A
0x1A3A0  je   0x1A3BE                 ; A==0 → 放行
0x1A3A2  cmp  byte [rbp-0x5F], r14b   ; flag B
0x1A3A6  jne  0x1A3BE                 ; B!=0 → 放行
0x1A3A8  mov  ecx, 0xFFFE7951         ; -100015
0x1A3AD  call 0x140925360             ; 抛异常
```

`0x140885310`（实际 `0x140885330`）内部：

```asm
0x8853A1  call qword ptr [rip + 0x11fe49]   ; IAT 0x9A51F0
```

这是进程快照类 API（`CreateToolhelp32Snapshot` 一类），拿到进程列表后遍历比对宿主。

**判据：flag A != 0 且 flag B == 0 时报错。**

## 阶段 11 · 一字节解决

### 补丁

文件偏移 `0x197A6`：

```text
before: 74 1C 44 38 75 A1 75 16 B9 51 79 FE FF
                        ^^
after : 74 1C 44 38 75 A1 EB 16 B9 51 79 FE FF
                         0x75 → 0xEB   (jne → jmp)
```

`jne +0x16` 变成 `jmp +0x16`，无条件跳到放行路径。

### 验证

```powershell
lyra-cli-patched.exe -v
# lyra-cli version dev-dd61f478 (commit , 2026-09-15 00:00:59)
```

```powershell
lyra-cli-patched.exe material --help
# Search and download materials (stickers, audio, ...) from the Jianying/Capcut platform.
# SUBCOMMANDS:
#   search      Search assets by type and natural-language intent.
#   download    Download an asset file by type and resource ID.
#   query       Inspect metadata for a known material resource ID.
#   topic       Browse material topic collections...
#   recommend   Fetch a recommended / hot material list...
#   similar     Fetch similar materials seeded by an existing resource ID.
#   motiongraph MotionGraph runtime-data generation...
```

```powershell
lyra-cli-patched.exe material search --type music --prompt "温暖的钢琴 治愈" --limit 5
# {"err_code":0,"err_msg":"success","result":{"items":[...5 首...]}}
```

### 自动化

```text

patch offset = PREFIX 命中位置 + 6
```

`src/lyra.py` 每次运行先检查补丁是否有效，失效就重建；找不到特征码就抛错（不会乱改字节）。

## 最终结论

### 成立的三个基石

1. **草稿是明文 JSON** —— 写文件就能控制剪映，不需要对抗任何东西
2. **剪映自带 `lyra-cli`** —— 官方 CLI，素材能力齐全，只需绕过 1 个字节的宿主校验
3. **草稿目录是普通文件系统** —— 部署 = 复制 + 注册，不需要 API

### 走过的死路

| 死路 | 卡在哪 |
|---|---|
| UI 自动化 | 剪映 11.5 QML 渲染，UIA 暴露 0 控件，`PrintWindow` 全黑 |
| 逆向引擎 DLL | `openSession` 抛 `0xe06d7363`，`invokeJsonRequest` 访问违例 + 堆损坏 |
| 伪装父进程绕过校验 | Procmon 证明是静默退出，不是真通过 |
| 解 CEF cookie | DPAPI 绑用户，换机器就废 |
| 只用本地缓存 | 覆盖不了"搜新的" |

### 关键数字

| 项 | 值 |
|---|---|
| 从零到可用 | 一轮完整会话 |
| 决定性的补丁 | **1 个字节** |
| 补丁搜索用的特征码 | 13 字节 |
| 支持素材类型 | 34 种 |
| MCP 工具 | 21 个 |
| 清理掉的垃圾 | 1.77 GB + 39 个脚本 + 6 个草稿 |

### 最大的教训

> **先确认"能不能用简单办法做到"，再决定要不要深入逆向。**
>
> 阶段 4 花了大量时间逆向 `videoeditor.dll`，全部失败；
> 而真正解决问题的，是阶段 2 的一句"草稿是明文 JSON" 和阶段 11 的一个字节。
