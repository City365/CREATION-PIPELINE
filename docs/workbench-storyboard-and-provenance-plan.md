# 创作台分镜管理与生成资料留存实施计划

日期：2026-10-25。状态：待实施；本次只提交已有代码并制定计划。
代码基线：5134aa4（当前创作功能集成及管理器上传修复快照）。

## 1. 目标与使用方式

完成以下四项需求：

1. 图像创作台生成的图片保存到素材库后，打开资料卡能够查看、复制生成时的完整提示词。
2. 视频在媒体库打开时能够查看、复制完整生成提示词，并查看相关参考图与参数，方便复刻。
3. 视频创作台左侧增加分镜目录，支持新建、重命名、拖拽排序、上移/下移、复制和删除。每个分镜独立保存工作台内容及历次生成结果。
4. 图像创作台左侧增加相同管理器，每个条目独立保存提示词、参考图、源图、生成结果和参数。

两种目录都按项目隔离，图像与视频各有自己的目录。首期使用平级分镜列表，名称可自由编辑；不引入复杂的文件夹层级。图像条目默认命名“画面 001”，视频默认“分镜 001”。

| 位置 | 当前行为 | 实施要求 |

现有场景建模、图像编辑和媒体剪辑继续使用现有功能入口；本轮新管理器主要管理图像/视频生成工作台。场景建模文档与剪辑工程仍由原存储负责，不在这轮混合迁移。

## 3. SQLite 数据设计

复用配置 dataDir 下的 studio.db，使用现有 node:sqlite DatabaseSync。通过 schema_version 表执行可重复的版本迁移，开启外键约束；迁移前备份数据库及需要导入的 JSON 文件。数据库、账号信息和生成媒体继续排除在 Git 外。

建议增加以下表：

| 表 | 关键字段与职责 |
| --- | --- |
| workbench_items | id、project_id、kind(image/video)、title、position、draft_json、revision、created_at、updated_at、deleted_at；保存当前可编辑工作台 |
| workbench_selection | project_id、kind、active_item_id；记住每个项目两种工作台各自选中项 |
| generation_runs | id、item_id、project_id、kind、job_id、status、snapshot_json、created_at、finished_at、error；保存每次生成时的不可变输入及任务状态 |
| media_records | id、run_id、kind、path、name、created_at；文件与生成来源的稳定关联 |
| media_locations | media_id、normalized_path（唯一）；登记复制、重命名、移动后的可查询路径，同一生成结果可在多个库中出现 |
| migration_log | source_key（唯一）、imported_at、details；避免旧草稿与历史重复导入 |

索引覆盖 project_id+kind+position、item_id+created_at、job_id、normalized_path。草稿和快照使用结构化 JSON 保存差异较大的图像/视频参数，目录、任务和媒体关系通过外键维护。媒体文件保留在磁盘，SQLite 记录元数据和路径，不存图片/视频二进制。

### 生成快照内容

- 用户原始提示词、叠加风格后的提示词；管理器返回的实际发送文本及图片绑定信息在可获取时另外保存。
- 区分“用户提示词 / 提交提示词 / 实际发送文本”，缺失的信息标记未记录，不推测补齐。
- 渠道 ID、渠道名称、供应方、模型、工作流 ID；不保存 API Key、Cookie、签名下载地址等凭据。
- 图像：尺寸、数量、质量、源图、有序参考图、风格 ID 及生成结果。
- 视频：时长、比例、分辨率、种子、采样参数、有序参考图、主体名称、参考音频及任务 ID。
- 参考素材保存当时的顺序与标签映射，避免后来重排图片导致旧记录中的 Picture 1 指向别的图片。
- 渠道已删除或参考文件丢失时仍能查看快照；恢复工作台时明确提示需要重新选择。

## 4. 页面与交互

### 左侧管理器

布局为“分镜目录 → 当前提示词/参考图参数面板 → 结果舞台/画布”。目录约 220px，支持收起；窄屏改成可展开面板，保留现有参数面板宽度调整功能。

目录条目展示编号、标题、缩略图、生成状态及最近修改时间。左键选中；条目菜单提供重命名、复制、上移、下移、删除。拖拽显示落点，排序一次事务提交；上移/下移提供无需拖拽的替代操作。

点击条目恢复其提示词、参考素材、参数和生成历史。切换项目前与切换条目前先保存当前草稿；保存失败时保留当前内容并提示重试，不能静默切换后丢失编辑。

删除采用软删除并提供恢复入口，不删除已生成媒体，不取消后台任务；正在运行的任务始终归属原条目。删除全部条目后显示空状态及“新建”按钮。

### 图像与视频独立状态

视频条目保存当前工作流/渠道、完整提示词、参考图/音频、时长、比例、分辨率、种子和生成历史。舞台和任务列表只显示当前条目记录。

图像条目保存生成/编辑/反推模式、提示词、反推文本、渠道、尺寸、数量、源图、参考图、结果列表及当前选中结果。画布基础参数可恢复；大体积撤销位图栈不放进草稿 JSON。未保存的画布编辑切换前需要完成保存或保留当前项，不能默默丢弃。

生成过程中可切换条目。异步请求必须捕获发起时的 item_id、run_id 和输入快照，完成后更新该条目的结果；禁止通过全局 state.image 或 lastJobId 将结果写入后来选中的条目。

### 素材库与媒体库资料卡

沿用当前应用内弹窗预览，增加：

- 完整提示词区域，支持展开及一键复制，按实际记录区分用户输入和提交文本。
- 模型、渠道、生成时间、种子、比例/尺寸、时长等可用参数。
- 有序参考图缩略图、来源项目/分镜、生成任务和结果版本。
- “在创作台打开”：定位仍存在的原条目；“用此记录新建”：按快照创建新条目再编辑，不直接启动生成。

列表只带摘要及媒体 ID，完整资料通过详情接口读取。历史记录缺失时显示“未记录生成提示词”，不使用当前工作台内容冒充原提示词。提示词以文本渲染并转义，避免 HTML 注入。

## 5. 后端接口与一致性

建议由 workbench-store.js / workbench-routes.js 管理目录和草稿，generation-store.js 管理生成快照及媒体索引；app.js 中抽取 workbench-manager.js 处理通用目录交互，避免继续将全部逻辑堆到单个文件。

建议接口：

- GET /api/workbench/items?projectId=...&kind=image|video
- POST /api/workbench/items：新建或根据记录复制。
- GET /api/workbench/items/:id：获取草稿及分页生成记录。
- PATCH /api/workbench/items/:id：带 revision 更新名称或草稿。
- POST /api/workbench/items/reorder：项目、类型、完整 ID 顺序及列表版本。
- POST /api/workbench/items/:id/delete、/restore：软删除及恢复。
- PUT /api/workbench/selection：保存当前选中项。
- GET /api/media/details?path=...：查询完整来源、快照、参考素材和记录状态。

所有写入校验项目归属、条目类型和 revision；冲突返回 409，前端保留本地编辑供重试/另存。排序校验同项目同类型 ID 完整且无重复，事务更新。自动保存防抖、单条目串行写入；旧项目返回较慢的读取响应不得覆盖新项目状态。

/api/jobs 与 /api/images/generate 新增 projectId、itemId；后端确认关联合法后先保存输入快照，再执行生成。视频队列重试/继续沿用原分镜归属，新参数生成创建新 run，不能改写原快照。媒体生成成功后登记文件路径，重命名/移动/另存同时更新索引；复制失败不登记成功记录。

文件详情与旧历史读取沿用并收紧现有授权根目录检查，使用 path.relative 判断范围，不能通过任意 path 参数读取其他目录。

## 6. 旧数据迁移

1. 备份并建立 schema；保留旧 studio_state、jobs.json、图片历史 JSON、任务目录及媒体文件。
2. 每项目旧视频草稿导入一个“原视频工作台”条目；首次加载时将尚未同步的本地草稿提供为恢复项，避免覆盖服务端较新记录。
3. 导入图片历史，每批建立生成记录；有可靠项目来源才归入该项目，否则放入“未归属历史”供用户选择导入，禁止全部塞进当前项目。
4. 根据 jobs.json、params.json、prompt.txt 恢复视频历史；提示词优先使用明确的完整原记录，记录来源和缺失字段。
5. 通过可靠原路径或已有结果 ID 建立媒体关联。对于以前复制到素材库且已丢失关系的图片，只有内容哈希能唯一匹配且来源元数据一致时才自动补关联；同图多次生成、来源歧义或缺失时保留待确认状态。
6. 迁移具备唯一 source_key，可重跑且不重复创建条目；迁移报告显示导入数量、缺失文件和无法关联数量。

第一阶段只新增 SQLite 元数据，旧队列 JSON 继续运行；不要将整个视频调度器数据库迁移与本次目录功能捆绑。后续可另立任务迁移队列。

## 7. 分阶段实施与验收

### A：完整提示词与媒体来源（先交付）

实现 SQLite 表及迁移、图片/视频生成快照、图片另存来源传递、媒体详情接口与资料卡。先解决“过后找不到提示词”。

验收：超过 160 字的完整视频提示词可查看复制；图片生成后修改当前提示词，再存原结果到素材库，仍显示生成时原文；文件移动/重命名后仍能查到来源；旧 prompt.txt 可回读；历史未知提示词如实显示缺失。

### B：视频分镜管理器

实现左侧目录、独立草稿、SQLite 自动保存、排序/重命名/复制/删除恢复、任务归属和分镜生成历史。

验收：两个分镜使用不同提示词和参考图，交替切换、刷新及服务重启后均保持独立；拖拽及按钮排序均持久化；后台任务完成不会串到另一个分镜；删除分镜不损坏既有视频。

### C：图像分镜管理器

复用通用目录，接入图像模式、参考图、源图、结果列表、历史和画布切换保护。

验收：图像 A 请求未完成时切到 B，A 的结果仍归 A；各条目的提示词、参数、源图和结果在刷新后正确恢复；两个项目之间不串数据。

### D：迁移、恢复与端到端验证

补齐媒体卡“定位原分镜 / 用记录新建”、历史迁移报告和错误恢复；执行数据库与浏览器验收。

验证覆盖：revision 冲突、重复迁移、错误项目 ID、排序跨项目注入、长提示词、多次生成快照不可变、上传失败、失效渠道、缺失参考图、重启恢复、未保存画布切换。

生成业务测试使用本地模拟渠道和测试媒体，通过正式 API 路径完成闭环；豆包/Gemini 只做上传、标签绑定及发送前准备，不点击视频生成、不消耗生成额度。单元测试通过与真实浏览器验收分别记录，不能互相替代。

## 8. 交付及回滚

每阶段单独提交 Git，记录变更与验收证据。交付包括数据库迁移、前后端实现、迁移报告、使用说明和浏览器验收记录。

旧数据库及 JSON 备份保留，SQLite 迁移以新增表为主；回滚代码时仍能打开原单工作台及旧媒体，新增条目数据保留在数据库中。回滚不能删除新生成文件。
