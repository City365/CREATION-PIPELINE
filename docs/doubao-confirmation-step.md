# 豆包方案确认步骤（2026-10-25）

## 机制

豆包视频模式不会直接开始生成：它先回复一份参数与分镜方案，末尾写“确认后我再开始生成视频。”，需要再发一条确认消息才开始。管理器的处理在 src/automation.js：识别到方案回复、文本停止变化满 15 秒后，自动在原会话发送一次“确认，开始生成视频”，并写入 `confirmationSentAt`，之后不再重复发。

## 这次查到的两个隐患

1. 锚点只按文本比对。`readPageState` 原来用“发送文本与页面上用户消息相等”来找本次提交的那条消息。原生图片引用会把 `<Picture N>` 替换成文件名卡片，渲染文本和提交文本对不上，锚点就找不到；锚点空 → `replies` 为空 → `text` 为空 → `state.confirmation` 永远是 false，确认消息永远不发，任务一直停在“等待本次会话回复”。
   - 现在先按文本匹配；匹配不上时，如果本次只新增了一条非附件、非“确认”类的用户消息，就直接认它作锚点。
2. 图片附件气泡可能排在文字消息后面。豆包把我们上传的参考图渲染成独立的气泡，顺序不固定。旧逻辑只允许附件气泡排在锚点之前，排到后面就被判成“额外用户消息”并中止任务（任务 cee0cec8 在 09:14:58 的 17 秒失败就是这一类症状，当时还没写诊断，无法逐条核对具体消息）。
   - 现在任务实际带参考图时，紧邻锚点的附件气泡都算本次提交；纯文字的第二条消息仍然会中止。
3. 视频模式会给用户消息加“生成视频：”前缀和参数后缀。确认消息的识别兼容这个前缀，避免确认被当成陌生消息。
4. “额外用户消息”的报错现在会把会话里的用户消息摘要写进错误和 `ownershipDiagnostics.messages`，下次再出现能直接看出是哪条。
5. 诊断上线后立刻抓到真正原因：豆包会给我们自己的参考图单独渲染一个空用户气泡，检查时图片还没画上去，`attachmentOnly` 判定为 false（因为没有 img），于是被当成“额外用户消息”。任务 0f4ea1d9 就是这样在提交后 17 秒被中止。现在正文为空的用户气泡只要紧邻锚点且任务带参考图，就算本次提交。

## 账号为什么被钉死

H3 的 `pickAccount` 即使渠道里“指定账号（可选）”留空，也会自己取该平台第一个账号并把 `accountId` 写进提交体；管理器把它存成 `requestedAccountId`，调度时只认这个号。于是那个号配额一满，任务就永远停在“等待可用账号：今日配额、冷却或占用限制”，其他号在旁边闲着。

现在 H3 只在明确选了账号时才传 `accountId`；留空时由管理器按配额/冷却/占用自动挑号，某个号被平台判定额度用尽时也会换下一个号。

## 账号轮换（管理器侧）

原来只有“任务没指定账号”时才会在平台判定额度不足后换号；H3 每次都指定账号，所以这条路径永远不触发。现在调度规则改成：

- 指定的账号**优先**，可用就用它；
- 它今日配额已满、在冷却、正被别的任务占用，就换同平台其他可用账号，任务消息会写“指定账号当前不可用，改用「X」”；
- 平台在执行中判定这个号额度用完（`ACCOUNT_QUOTA_EXHAUSTED`），把该号加入 `excludedAccounts` 并重新排队，换下一个号继续，不会直接判任务失败；
- 只有同平台所有账号都不可用时，才显示“等待可用账号：今日配额、冷却或占用限制”。

## 人工验证

新账号第一次跑、或豆包风控触发时会弹人机验证。这时管理器会暂停任务，并把账号窗口提到最前，任务消息写“豆包要求人工验证：请在账号窗口里完成滑块/验证后不要关闭窗口，任务会自动继续”。验证完成后任务自动继续；“不会动”不是卡死，是等人在窗口里点一下。

如果这时候把窗口关掉，任务会以“账号浏览器窗口被关闭，任务已中断”结束（以前只显示 `Target page, context or browser has been closed`，看不出原因）。
