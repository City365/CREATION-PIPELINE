## DEC-001 现在不切换到 MySQL/PostgreSQL（2026-11-05 用户确认暂缓）

- **2026-11-05 用户决定**：「先不要迁移，就使用 SQLite，后期功能全部开发完成后再对接改造，不着急。」

- 原基线与问题：用户明确「数据库后续会改为 MySQL 或 PG 远程连接，不可能放在本地，现在只是测试，本地都没弄好」。
- 事实证据：
  - 现有数据访问全部是 `node:sqlite` 同步 API，共 147 处 `.prepare`、76 处 `.exec`（01 §2.2）。
  - `mysql2/promise`、`pg` 只有异步 API（SRC-002）。
  - 调度器 `events.js`、`jobs.js`、`image-tasks.js` 的运行时模型依赖同步读写。
  - 当前没有可用的 MySQL/PG 实例，无法做迁移与恢复验证。
- 方案比较：
  1. 立即换库：改动面覆盖 147 个调用点与任务泵，且无实例验证，回归风险极高；不满足「避免大量 bug」。
  2. 先修本地正确性 + 建立端口/异步化设计，再分阶段迁移（推荐）：本轮可验证，迁移路径明确。
  3. 维持现状不做任何准备：后续迁移成本更高。
- 推荐：方案 2。
- 具体差异：本轮新增 `jobs` 表（SQLite），04 §5 交付调用点/方言/顺序清单；不新增数据库依赖。
- 用户需决定：是否批准下一阶段（端口 + 异步化）作为独立任务；需要提供 MySQL 或 PG 测试实例。
- 审批记录：用户已要求「按规范执行、完整链路」；2026-11-05 明确暂缓迁移、继续 SQLite，等功能开发完成后再评估。
- 实施与关闭：本轮不换库；REQ-008 暂缓，用户决定功能全部开发完成后再评估迁移。

## DEC-002 任务状态保留内存工作集，按行持久化

- 问题：把 `jobs.js` 整体改成异步/数据库驱动会牵动调度器、插件、工作台。
- 方案：
  1. 全量重写为 async repository（彻底，但风险高）。
  2. 内存工作集 + 脏行批量 upsert（推荐）。
- 推荐理由：保持现有同步调用与插件契约，消除全量写与 JSON 并发覆盖；后续异步化时只需替换 repository。
- 差异：`jobs.js` 新增 `jobRepo` 与 `dirtyJobs`；对外 API 不变。
- 审批：属于本轮规范内的持久化修复，不改变业务契约。

## DEC-003 密钥先脱敏、后入库加密

- 问题：`config.json` 明文密钥且响应泄露。
- 方案：
  1. 先确保响应不泄露，再加密入库（推荐）。
  2. 两步一起做（当时改动过大）。
- 结果：两步均已完成——TASK-003 接口脱敏；TASK-006 密钥 AES-256-GCM 入库、`config.json` 脱敏。租户级渠道隔离仍未做，转 TASK-007。

## DEC-004 执行端过期命令由双端共同丢弃

- 问题：超时命令残留队列，可能延迟执行。
- 方案：
  1. 仅服务端移除（无法阻止已下发命令）。
  2. 服务端移除 + 命令带 `expiresAt`，管理器执行前校验（推荐）。
- 推荐理由：双向保护，旧版管理器忽略新字段仍兼容。
- 差异：`executor-channel.js`、`manager/src/outbound.js`。

## DEC-005 租户配置用 AsyncLocalStorage，而不是给所有调用点加 tenantId

- 问题：48 处 `config.load()`、36 处 `channels.*` 调用，逐个加参数改动面大、容易漏。
- 方案：
  1. 显式传 `tenantId` 到每个函数（改动面最大，类型/调用链都要跟进）。
  2. 请求/任务级 `AsyncLocalStorage`，`config.load()` 读当前租户（推荐）。
- 推荐理由：调用点不变；后台任务按任务记录切上下文；测试可以直接 `tenantContext.run`。代价是隐式上下文，必须覆盖请求入口和所有后台泵。
- 差异：新增 `tenant-context.js`/`tenant-scope.js`；任务/事件/图像任务记录 `tenantId`；请求入口用 `run('')` 包裹，认证后 `enter`。
- 验证：TC-021..027，含「无上下文泵任务」和「keep-alive 请求不串租户」的机制测试。

## DEC-006 配额按「任务事件/天」计数，0 表示不限

- 问题：需要限制租户资源，但生成链路上有单条、批量、草稿、定时、重试多种入口。
- 方案：
  1. 按每次生成条目计数（更精确，但批量和重试边界复杂）。
  2. 按新建任务事件计数（一个批次算一次；重试沿用原事件不重复计）。
- 推荐：方案 2。入口集中、计数稳定，超限在 `events.createFromJobInputs` 一处拦截；直接图像重试不重复计。
- 配额默认全为 0（不限），避免升级后突然阻断现有用户。
- 审计写入采用 best-effort：失败只写 `process.log`，不影响业务；每租户保留 5000 条。
- 权限：渠道/租户配置只有 owner/admin 可改；成员只读，避免普通成员改掉全租户的渠道。

## DEC-007 界面偏好写用户表，平台配置只作默认值（2026-11-05）

- 问题：`ui` 是平台共享，一个人改主题会影响所有租户。
- 方案：`user_prefs` 每用户一行，保存显式改过的键；`config.json.ui` 保留为默认值；未登录本机仍写平台默认。
- 理由：改动集中在 `/api/config` 与 `/api/state`，不动前端保存逻辑；删用户时清理。
- 代价：平台管理员没有“改所有用户默认主题”的界面，只能改 `config.json`；后续需要再加。

## DEC-008 智能体默认 controller，内部项目接口按 ID 校验（2026-11-05）

- 问题：默认 `development` 直接放行；controller 模式调 `/api/projects` 只能看到默认租户。
- 方案：新增 `/api/internal/projects/:id`（本机 + 内部 token），返回任意租户项目；启动脚本默认 controller；`/agent/health` 公开；测试夹具显式 development。
- 理由：安全默认；不把租户上下文带进智能体；代理层已完成租户校验。
- 代价：单独启动智能体且没有控制器时，业务接口会 503；这是预期的 fail-closed。

## DEC-009 密钥轮换用 next 文件 + 启动收尾（2026-11-05）

- 问题：换 `secret.key` 需要重加密全部密文，文件与数据库无法原子提交。
- 方案：先写 `secret.key.next` 与 `meta.vault_rotation`，事务更新密文，成功后备份旧 key 并改名；启动时 `recover()` 用 next 试解密，成功则收尾、失败则删除 next。
- 理由：把“事务已提交/文件未换”的崩溃窗口变成可恢复状态。
- 代价：环境变量 `WMD_SECRET_KEY` 生效时拒绝文件轮换，需要改环境变量并重启。

## DEC-010 审计用每租户哈希链，不是防篡改存储（2026-11-05）

- 问题：审计表可被直接改；需要可验证的证据。
- 方案：每租户 `hash = sha256(prev_hash|...|created_at)`，`verify()` 从最早一条非空 hash 记录开始校验；清理保留 5000 条会移动锚点。
- 理由：实现小、能发现改单条/删中间条；不改变现有查询与权限。
- 代价：有数据库写权限的人可以整链重算；真正的防篡改需要外部 WORM/签名服务。
