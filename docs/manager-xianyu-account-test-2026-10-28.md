## 测试约束

按要求**不发送“确认，开始生成视频”**，避免消耗账号配额。因此本轮只验证到发送前一步：

```

→ 上传参考图 → 提示词里 @图1 绑定附件 → 填入提示词 → 停在发送前

```

该入口使用 `createExecutor({prepareOnly:true})`，`submitText` 的发送回调返回 `false`，只填写不点击发送。

## 发现的问题

### 问题 1（已修复，高频）：豆包「下载电脑版」弹窗不会自动关闭

- 现象：豆包网页随机弹出「下载电脑版 · 使用完整功能」引导弹窗，整页遮罩拦截点击。管理器的 `settlePopups` 只会等待弹窗自己消失（最长 120 秒），不会识别和关闭。
- 影响：闲鱼 3 首次测试在点击视频参数面板时被遮罩拦截，15 秒点击超时，整轮 142 秒后失败。
- 证据：`Video-Generation-Manager/data/popup-probe.png`（弹窗原文与按钮）。
- 修复：`settlePopups` 增加 `dismissBenignPopup`：只识别「下载电脑版 / 使用完整功能」这一类引导弹窗，优先点「下次提醒我」，失败再点关闭按钮（aria-label=关闭）；验证、确认、额度类弹窗不碰。同时在 `prepareInputs` 填完输入框后先处理一次页面弹窗。

### 问题 2（已修复，竞态）：技能条未渲染就开始找「视频生成」

- 现象：页面输入框先出现，底部技能条（视频生成 / 图像生成 / 更多技能）还没渲染，管理器立即尝试三种入口，全部找不到，5 秒内直接失败。
- 影响：闲鱼 3 稳定性复测中出现一次 `页面含「视频生成」文字：无；更多技能按钮 0 个`。
- 证据：`Video-Generation-Manager/data/doubao-tag-draft-failed.png`（截图里只有输入框，没有技能条）。
- 修复：进入视频模式前，最多等 20 秒让 `[data-testid^="skill_bar_button_"]` 出现，再开始尝试入口。

### 问题 3（已修复）：入口点击顺序会先点到文本副本

- 现象：`getByText(/^视频生成$/)` 会同时命中按钮和按钮里的 `span` 副本，先点嵌套节点可能不触发按钮事件，白等点击超时。
- 影响：闲鱼 4 首次测试三种入口均未进入视频模式，112 秒后失败；单独用 Playwright 点 `[data-testid="skill_bar_button_17"]` 可以正常进入。
- 修复：`clickVideoEntry` 改为优先点 `[data-testid^="skill_bar_button_"]` 且文本为「视频生成」的按钮，再退回文本匹配和 JS 兜底。

### 问题 4（未完全定位，偶发）：参数面板点击被未知弹层拦截

- 现象：闲鱼 5 首次测试在点击视频参数面板时，被一个 `role="dialog"` 的弹层拦截，15 秒点击超时；同一账号复测通过。
- 现状：该弹层不是「下载电脑版」引导（否则会被问题 1 的修复关掉），本次没有抓到它的文本，可能是豆包随机的新功能提示或参数面板自身的浮层状态。
- 建议：后续在 `applyOptions` 点击参数前再抓一次可见弹层的文本；如果确认是无害提示，加入 `dismissBenignPopup` 的白名单。

### 问题 5（已修复）：`更多技能` 按钮有多个同名副本

- 现象：闲鱼 4 页面里 `[data-testid="skill_bar_button_more"]` 有 3 个（其中两个文本为空）。错误信息里的「更多技能按钮 3 个」会让人误判页面没有入口。
- 现状：`openSkillMenu` 已经固定点第 1 个并用 JS 兜底，功能不受影响；只是诊断文案不准确。
- 修复：诊断改为只统计可见控件，并列出可见技能条按钮的文字，例如「可见「更多技能」按钮 1 个；可见技能条按钮：视频生成 / PPT 生成 / 更多技能」。

### 问题 6（已修复）：草稿失败时没有现场截图

- 修复：`reference-draft.js` 在异常分支也截一张 `doubao-tag-draft-failed.png`，便于定位页面状态。

### 另一次异常（未复现）

- 第一次通过正式任务接口提交闲鱼 1（5 秒、无参考图）时，15 秒内报「账号浏览器窗口被关闭」，任务失败；记录显示没有发送确认、没有扣配额。当时用户正在观察弹窗，可能是人工关闭窗口或页面弹窗导致，未复现。

## 确认话术与多轮催促

### 随机确认话术

原来每次都发固定的「确认，开始生成视频」。现在改为从 9 条语义相近的话术里随机取，同一进程内洗牌取词、不会连续重复：

```
确认，开始生成视频
确定，生成视频
可以生成视频吧
好的，请开始生成视频
没问题，直接生成视频
同意，开始生成吧
快点，给我生成视频
就按这个生成视频
开始吧，生成视频
```

实际发送的话术会写进任务记录的 `confirmationPhrase` 字段，便于以后核对。

### 平台先说“不能生成”时的多轮请求

`page-state.js` 新增 `videoUnavailable`，从**最新一条助手回复**里识别这些说法：

- “我现在无法直接生成视频…”、“暂时不能生成视频…”
- “不支持视频生成”、“视频生成暂不可用”
- “只能提供文字方案，无法生成视频…”

命中后，`automation.js` 在回复稳定 8 秒后从催促话术池里取一条再发，最多 3 轮：

```
我确定要生成视频，请按上面的提示词直接生成
请继续，用刚才的描述生成视频
不需要文字方案，直接生成视频
可以生成，开始吧，生成视频
请帮我生成视频，就按上面的内容
我确认要生成，直接开始生成视频
用上面的提示词生成视频，谢谢
```

每轮都会写 `pushRounds` 到任务记录；3 轮后仍不进入生成就停止催促，继续等待或按超时处理。催促消息和确认消息都会加入本轮的“任务回复白名单”，页面归属检查会把它认作自己发的，不会误报“任务会话出现额外用户消息”。

## AI 回复理解与技能聊天

原来的确认/催促判定完全依赖正则。现在新增了一个可选的小模型“回复理解器”，把语义判断交给模型，正则降级为兜底。

### 配置（系统设置）

- 位置：系统管理 → **AI 回复理解与技能**。
- 字段：启用、协议（OpenAI 兼容 / Anthropic 兼容）、Base URL、模型、API Key、超时；「从智能体导入」会读取 `Creation-Studio/agent_backend/data/agent_settings.json` 当前启用的 provider，Key 只保存、不回传浏览器。
- 预算：上下文约 200k、单次输出上限 10k；Anthropic 协议显式关闭 thinking，避免 thinking 吃满 tokens 导致正文为空（实测 320 tokens 会被 thinking 全部吃光）。

### 测试页（/interpreter）

- 入口：顶栏「回复理解」；页面只做聊天测试，模型配置通过右上角「模型配置」跳到系统设置。
- 模式：
  - **豆包实测**：选账号直接聊；`POST /api/accounts/{id}/chat-test` 在同一个账号页面/会话里连续发送普通对话，不进入视频模式、不点确认、不消耗视频额度；如果页面已在视频模式会先切回，切不回来直接报错。
  - **智能体对话**：`POST /api/agent/chat`，由管理器的模型按勾选的技能回复，可连续多轮；账号栏自动隐藏。
- 技能（`GET /api/skills`，定义在 `src/skills.js`）：
  - **语义理解**（intent）：对回复做意图判定，显示 intent、置信度、下一步、判定依据。
  - **正常对话**（chat）：注入“AI 视频创作专家”的对话提示，优先使用管理器里的豆包 / Gemini；同时显示建议回复和「用它回复」按钮。
  - 勾选结果保存在浏览器 localStorage（`creative-desk-skills`）；新增技能只需在 `src/skills.js` 增加一条。
- 判定输出：`intent`（confirm / soft_refuse / hard_refuse / ask_info / generating / done / other）、`confidence`、`evidence`、`next_action`、`suggested_reply`。
- 任务执行：每条新的助手回复只判定一次（按消息 key 缓存）。模型判为 confirm 且置信度 ≥0.75 才确认；soft_refuse / ask_info 继续请求；hard_refuse 直接停止。模型不可用、超时或 JSON 无法解析时自动退回正则。判定写入 `replyUnderstanding`，确认来源写入 `confirmationSource`（ai / rule）。
- 实测：
  - 豆包两轮（闲鱼 1）：第一轮判 confirm 0.97；第二轮豆包改口「没办法直接一键出视频文件」→ 判 soft_refuse 0.95。
  - 智能体模式（技能：语义理解 + 正常对话）：智能体给出豆包视频提示词和参数；理解器判为 soft_refuse 0.85，建议回复「别只给方案，直接帮我生成视频…」。
  - 全程没有点确认，未消耗视频额度。

### 任务失败原因回填

- 任务失败时，管理器把原始错误、任务提示词、平台/账号、最后一条助手回复和页面状态（是否在生成、是否要求验证、是否额度不足等）交给同一个模型，输出 `failureAnalysis`：`{category, reason, advice, confidence}`。
- 类别：`login` / `captcha` / `entry` / `upload` / `platform_refusal` / `quota` / `network` / `download` / `timeout` / `unknown`。
- 任务记录的 `message` 改为模型给出的中文原因，`error` 保留原始错误；同时写入 `failureCategory`、`failureReason`、`failureAdvice`、`failureAnalyzedAt`。模型不可用或输出无法解析时，仍用原始错误。
- 控制台 `manager-video.poll` 读取 `failureAnalysis`，`jobs.js` 把原因和建议拼进任务错误（「管理器任务失败：…（建议：…）」），任务详情能看到更准确的原因。
- 真实 DeepSeek 实测三条：
  - 入口改版 → entry：「页面有「视频生成」文字，但未找到可点击的视频模式入口，可能是入口位置或界面改版导致。」
  - 未登录 → login：「页面找不到聊天输入框，通常是未登录或登录已失效…」
  - 内容拒绝 → platform_refusal：「平台判定提示词内容涉嫌侵权，拒绝生成视频」
- 测试：管理器 103 项通过；控制台新增 `tests/manager-failure-analysis.test.js`，manager-video 集成测试通过。

## 执行前暖场（2026-10-28 追加）

正式提交提示词前，先以普通创作者的身份和豆包聊两轮漫剧、短剧、小说、视频创作，让会话上下文像正常的创作交流，再进入视频模式提交任务。

### 流程位置

```
打开账号页面 → 确认/新建独立会话 → 暖场（普通聊天 2 轮）
→ 进入「视频生成」→ 设置 16:9 / 5s → 上传参考图 → 填提示词 → 发送
```

暖场只发普通聊天消息：不进入视频模式、不点确认、不消耗视频额度。页面如果还停在视频模式，会先点「新对话」切回；切不回来就跳过暖场并在任务里记录原因。

### 话题生成

- 启用 AI 回复理解时（`src/warmup.js` → `planWarmup`），按任务提示词的主题让同一个模型生成两轮话题：第一轮聊通用创作话题，第二轮自然靠近任务主题，但不会复述提示词，也不会出现“生成视频 / 提示词 / 帮我做”这类指令。
- 模型不可用、超时或输出不合格时，退回内置话术池（10 条开场 + 8 条追问 + 连接词），同一进程内洗牌取词不连续重复。
- 每条消息都会附带“简短回答”的要求（例如“简单说两句就行，五十字以内”），否则豆包会写五六百字，暖场会慢到一分钟以上。

### 等待与失败处理

- 每轮发送后等豆包回复结束、文本稳定 800ms 再发下一条；单轮最多等 45 秒。
- 暖场任何一步出错（回复超时、找不到输入框）都只写入任务 `warmup.error`，任务继续走正常流程；浏览器窗口被关掉才中断任务。
- 暖场消息在后续任务里属于“已有历史消息”，归属检查不会把它们当成额外用户消息。

### 设置与记录

- 系统管理 → **执行暖场**：启用开关、轮数（1–3）、单轮等待毫秒数；默认启用、2 轮、45 秒。
- 任暖场期间任务状态为「暖场中」，列表会显示“执行前暖场：和豆包聊创作话题（1/2）”。
- 任务记录写入 `warmup`：`{rounds,total,source:'ai'|'pool',messages:[{text,reply,error}],finishedAt}`，任务明细里有「执行前暖场」一栏。

### 实测

- 闲鱼1（优化前）：两轮共 82 秒，因为豆包每条回复 500–700 字。
- 闲鱼2（加入“简短回答”要求后）：两轮共 14.9 秒，回复约 100–140 字；第二轮自动贴到任务主题“雨夜老房灯光”。
- 两次都只停留在普通聊天，没有进入视频模式、没有点确认、`quotaCharged=false`。

### 验证

- `npm test` 113 项通过（新增 `tests/warmup.test.js`：话题解析、兜底话术、模型调用与降级、页面发送与视频模式跳过、设置默认值与范围）。
- `npm run test:ui` 通过：5 个页面、移动端无横向溢出、无渲染错误（设置页新增暖场保存校验）。

## 任务会话归属检测（2026-10-28 追加：已移除）

- 现象：任务 `d7392c13`（自己号-用户490936，15s / 16:9 / 6 张参考图）在提交提示词后报「任务会话出现额外用户消息，已停止操作以避免混用结果」，会话里的“额外消息”正是暖场的两条聊天。
- 原因：判定依赖 `baseline` 里的消息 key，而 key 是管理器写在 DOM 的 `data-local-manager-message-key` 上的；平台在提交后重新挂载消息节点，属性和 key 丢失，暖场消息被当成新消息。

## 素材候选误判（2026-10-28 追加：已修复）

- 现象：任务 `b62dd57b`（闲鱼2，6 张参考图：陈建国 / 小刘 / 老周 / 王经理 / 办公室 / 主管办公室）在绑定 `@图5 办公室.png` 时报「豆包素材候选不唯一：办公室.png」。

## 账号调度改为池内随机（2026-10-28 追加）

- 现象：没指定账号的任务总是落到同一个号上，看起来像按顺序排队。
- 原因：`TaskQueue.drain` 在可用账号里按“今日剩余配额最多”排序取第一个。配额相同的账号保持存储顺序（创建顺序），所以永远先选到同一个；失败任务没有扣额度，剩余量不变，下一个任务还是它。
- 修改：指定了账号仍优先用它；没指定时在可用账号池（启用、平台匹配、未占用、有配额、不在冷却、未被排除）里**均匀随机**取一个。账号池随配额消耗自动收窄。
- 验证：管理器 116 项测试通过，账号调度用例改为固定随机数分别命中两个账号。
