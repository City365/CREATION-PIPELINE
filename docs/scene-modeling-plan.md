## 1. 结论

## 3. 现有项目可复用和缺口

## 4. 页面设计

左侧：场景名称、描述、参考素材列表（场景/线稿/平面图/材质参考）、推理模型选择、生图模型选择、开始分析/按要求修改。

右侧工作区：参考图、平面坐标、白模预览、四视图、线稿、分析报告。对象列表与属性面板联动；选择对象显示尺寸位置与来源，可编辑并锁定。支持显示/隐藏网格、轴向、对象编号、门扇扫掠、机位与视锥。

主操作按阶段出现：分析场景 → 查看并修正布局 → 生成结构线稿/白模 → 生成场景图。允许直接查看所有数据；不强迫用户填写坐标。

## 5. AI 流程

1. 输入整理：保留原始描述、每张素材角色和顺序，记录资料标识。
2. 多模态分析：先列可见物体、门窗、遮挡与透视线索，再提出空间草案；输出严格校验的结构化数据。
3. 约束求解：程序检查数据与几何，AI 根据具体冲突提出有限修订。锁定字段不得暗改；明确条件互相矛盾时展示选项等待用户处理。
4. 场景冻结：保存模型版本；派生平面图、机位、白模和提示词。
5. 出图：每个视角传入相应结构引导图、模型约束及适用的外观参考；不能把一次 count=4 当作四个指定机位。
6. 对照检查：图文模型辅助比对门窗所在墙、数量、相对位置和光向，列出疑点；保留用户人工确认状态。模型自检不等于几何证据。

推理与生图分开选择渠道。文本建模可用文本推理模型，图片分析必须使用支持图像理解的模型。现有协议适配支持图文输入，但不能由此认定每个已配置模型都支持视觉；实施时做最小真实能力验证并显示具体错误。

AI 输出仅作为数据解析，不执行其代码；字段缺失、非有限数值、未知对象引用等拒绝进入渲染。保留原始响应供排错；最多有限次数纠错，超时/取消停止后续阶段，重试只重跑失败步骤。

## 6. 场景数据

SceneDocument：schemaVersion、id、projectId、revision、原始输入、素材引用、模型/规则版本、单位/坐标约定、真实边界及不可用区、尺寸/层高、objects、openings、lights、cameras、constraints、issues、outputs。

每个关键属性记录来源：用户明确、图像观察、推定、用户修正；附依据和必要的不确定性说明。单图没有可靠比例尺时尺寸为推定，允许用已知门宽或房间尺寸重新定标。单图无法唯一恢复背面布局，保留未知区域与候选方案。

对象含中心 xyz、局部宽深高、朝向、真实占地多边形、父对象、材质及锁定字段。门窗含墙体或边段、区间、底高/顶高；门另含铰链和开向。摄像机含位置、目标、up、投影和水平/垂直视场约定，俯视指定北向。

输出引用模型 revision。布局变化后旧图保留但标记“基于旧布局”，避免混用。按项目存储场景和任务，不只保存在浏览器内存；保存后刷新可恢复。

## 7. 校验与预览

现有 check-layout.mjs 仅轴对齐占地、重叠与相机嵌入，不支持旋转占地、门窗、承载物底高、L 形边界或通路连通性。不能直接沿用其 ok=true 代表完整校验通过。

第一阶段：数值和 ID/引用校验、真实边界包含、旋转占地碰撞、高度区间、墙面开口区间、承载例外、机位落点和基本视向校验。规则独立返回“通过/冲突/未检查”，不混成一个笼统通过。

第二阶段：门扇扇形扫掠、使用空间、通路连通性与最窄宽度近似检查；明确近似精度。不能靠家具中心点代替真实占地。模型转为渲染引擎坐标时使用唯一转换层，单测验证 Z-up 与引擎轴向、旋转方向、相机 up。

平面图由程序绘制，带比例尺和可选标注；结构白模/线稿由同一几何模型和机位渲染。可采用轻量 WebGL 场景；对象先用具有真实尺寸的基础体块，并明确其为概念体块，而非从照片恢复的精细网格。

## 8. 线稿分类

A. 原图轮廓线稿：保持当前视角，用于描边/编辑参考。传统边缘算法只作为轮廓预览，不能称为干净建筑结构线稿；AI 净化需单独记录生成结果。

B. 模型结构线稿：由统一几何模型生成平面图和各机位轮廓，作为多视角生图的结构引导。默认保留遮挡；透视/正交参数共享。

C. AI 精细线稿：以结构线稿和外观素材为参考补充细节；不能把 AI 改动结构后的结果当作原模型真值。

导出支持 PNG；平面/线条数据可导出 SVG，场景文档 JSON 与完整 A/B/C/D Markdown。图纸标注层与生图参考层分开，避免编号/坐标被画入成片。

## 9. 素材与规则维护

现有用户文件夹以方法和文本样例为主，不是完整图片素材包。经实施时将规则、模板、例子复制为项目内部的版本化资源，不依赖桌面绝对路径；原资料保留。

内置青竹书房示例可直接预览坐标、对象和四机位。用户可追加场景图、平面图、线稿和材质参考，标注用途。不能把风格参考里的布局无意并入场景。

规则和风格模板可维护；将固定输出和坐标契约与可编辑风格分离，保存规则版本，避免改一条模板破坏已有场景。

## 10. 分阶段交付

一：Tab + 场景文档持久化 + AI 结构化建模/图片分析 + 来源/锁定 + 2D 平面图 + 基础校验。验收：描述/图像两种输入，修改单一对象不影响其他 ID，刷新恢复，明确尺寸冲突不被暗改。

二：可交互概念白模 + 四机位 + 结构线稿 + 旋转家具/门扇/动线检查。验收：同一模型的门窗位置跨视角一致，真实遮挡，俯视北上，线稿与平面坐标对应。

三：接通现有图像渠道的四视图/场景图/AI 净化线稿任务 + 参考图绑定 + 结果对照 + 局部重跑 + 保存素材库/发送视频。验收：实际模型返回可显示图片，不用 HTTP 200 代替出图成功；失败不整组重发、不混入旧版本输出。

第一批完整可用版本建议覆盖以上三阶段，逐阶段演示验收；精细网格重建、自动材质贴图、任意复杂建筑/CAD 工程能力另行扩展。

### 计划一推荐组合

场景模型/校验/AI 编排由本项目掌握，Three.js 负责白模和机位；miniPaint 先用于 PS 基础图像处理验证。两个编辑器共享素材引用，分别保存场景文档与图层文档，不混为一个不可维护的 JSON。

先实现 miniPaint 集成验证，检查：本地图片载入 → 编辑 → 带图层保存 → 刷新重开 → PNG 透明导出 → 回到当前素材/画布。它的入口源代码暴露 FileOpen/FileSave/Layers/State 等对象，但不能据此认定已有完整稳定的宿主通信 API；应建立自己的窄适配层，并固定上游版本。[入口源码](https://github.com/viliusle/miniPaint/blob/master/src/js/main.js)

同源独立页面/iframe 隔离其 CSS 和快捷键。宿主与编辑器仅交换项目 ID、文档 ID、资源引用和 Blob/受控内容；若采用 postMessage，检查来源窗口、origin、消息类型和请求 ID。图片不发送到第三方网站。中文字体、离线资源、撤销栈、导出内存都列入验证。

若该验证不能满足图层保存和稳定回传，再使用 Fabric.js 路线；在验证前不同时集成两套图像引擎，也不迁移整站为 React。当前简易基础编辑面板作为轻量入口保留，复杂编辑打开独立工作区。

### 图像编辑功能边界

首批：多文档关闭/切换、脏状态提示、图层新增/重命名/显隐/锁定/排序/透明度、选择移动缩放、裁剪旋转、画笔橡皮擦、文字、基础调色、导出 PNG/JPEG/WebP、带图层工程保存与恢复。

下一批：选区复制粘贴、蒙版/局部擦除、仿制与局部修补、透视调整、AI 选区编辑。具体工具先验证上游实现质量；不能把候选的工具列表直接当作本项目已交付。首批不承诺完整 PSD 往返、Photoshop 插件或专业印刷色彩链路。

AI 改图：将选定底图、区域蒙版和文字指令送入现有图像渠道；能力不支持蒙版时明确禁用对应入口。AI 结果成为新图层/新版本，不覆盖原图或场景几何。场景渲染出的线稿可进入图像编辑；修改的是导出图片，除非用户另行确认，不能反向改变场景对象坐标。
