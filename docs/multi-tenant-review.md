# 多租户改造评审：租户 → 用户 → 项目

状态（2026-11-05 更新）：主体已实现——租户/用户/项目隔离、外联通道、密钥加密入库、租户级渠道/提示词配置。剩余：配额与用量、审计、密码重置/邀请、每用户独立的管理器渠道配置。实现细节与验证见 `docs/delivery/creation-studio/`。

**范围约定（2026-11-05 补充）**：管理器（Video-Generation-Manager）是独立应用，安装在各用户自己的电脑上，一人一份、互不相干，**不纳入租户体系**，也不做任何多租户改造。本文只评审创作台（Creation-Studio）与智能体后端的隔离，以及「共享创作台如何连到每人本机的管理器」。

## 一、结论

现有系统只有 **项目** 这一层归属，而且这一层本身也没有强制校验（客户端传什么 `projectId` 就用什么）。
「用户」只存在于创作台的登录里，且**只允许一个账号**；「租户」完全不存在。

直接改成多人使用，目前会出现三类越权：

1. **跨项目读**：任何登录用户传别人的 `projectId` 就能读写项目数据（任务、分镜、素材、事件）。
2. **跨项目取文件**：`/api/media/file?path=` 的允许根目录包含**所有项目文件夹**。
3. **实时事件全量广播**：`/api/task-events/stream` 把所有人的任务事件推给所有连接。

管理器不在这个范围内：它天然属于「用户自己的设备」，数据留在个人电脑上，不需要租户字段。真正要解决的是 **创作台如何找到并调用「这个用户自己那台机器上的管理器」**（见第五节）。

## 二、现状盘点

| 数据 | 位置 | 现有归属字段 | 隔离程度 |
| --- | --- | --- | --- |
| 用户 | `data/users.json` | 无租户 | 全局只有 1 个账号（`auth.js:47` 第二个人注册直接报错） |
| 会话 | `data/sessions.json` | userId | 令牌 → 用户，30 天，无设备/无租户 |
| 项目 | `data/projects.json` | 无 owner、无 tenant | `/api/projects` 返回全部（`server.js:539`） |
| 任务 | `jobs` 状态 | projectId（可为 `unassigned`） | 只按项目过滤 |
| 事件/批次 | `data/events*` | `spec.projectId` | 只按项目过滤 |
| 创意文档（场景/图层） | `data/creative*` | 键是 `userId:projectId`（`creative-routes.js:239`） | 已带用户维度，但只能有一个用户 |
| 工作台条目/生成记录 | `data/*.sqlite` | `project_id` | 无用户 |
| 素材/媒体/上传/导出 | 项目目录下的 `assets/ media/ uploads/ exports/` | 项目目录即边界 | 文件接口的许可根是**全部项目目录**（`server.js:127-141`） |
| 全局配置 | `data/config.json` | 无 | 模型 Key、渠道、文件夹、**管理器地址**全局共享 |
| 智能体文件/知识库/会话 | `agent_backend/data/workspace`（SQLite） | `project` | 无用户；鉴权默认关闭（`harness/identity.py:33`） |
| 智能体项目校验 | `X-Project-Id` 头 | — | 默认 `development` 模式全部放行；`controller` 模式也只校验项目存在 |
| 管理器（本机独立） | 各自机器的 `data/*` | 不适用 | 一人一份，天然隔离；只有机器令牌 |

## 三、缺口清单（创作台 + 智能体）

### 1. 账号与认证层

- **没有租户实体**：需要 `tenants`，用户归属于租户；一个人能否属于多个租户要定策略（建议允许，登录后选租户）。
- **注册被写死为单账号**：`auth.js:47-49` 的逻辑要改成「首个用户 = 平台管理员」，租户内的用户由邀请或管理员创建。
- **没有角色/权限模型**：现在只有 `isAdmin` 布尔值。至少要有：平台管理员、租户管理员、普通成员（可选只读）。
- **会话缺少租户上下文**：`sessions.json` 只有 userId；要加 tenantId、可选的设备信息与最后活跃时间。
- **没有改密/找回/踢下线**：忘记密码只能删 `users.json`（这本身是个危险开关，见下条）。
- **登录开关是隐式的**：`auth.enabled()` = 有没有用户，`users.json` 被删掉后整个 API 变成**免登录可访问**（`server.js:467`）。多租户下必须改成显式配置，且默认拒绝。
- **没有审计**：登录、创建/删除项目、下载成片、改配置都没有留痕。

### 2. 项目与数据归属

- `projects` 记录没有 `tenantId`。所有项目平铺，任何人可见。
- `scoped(value)`（`server.js:475`）是 `客户端传的 projectId || 当前项目`，**客户端优先**——这就是越权入口。正确做法是先按 `(tenantId, projectId)` 查询归属，查不到直接 404。
- `jobs` 里的 `unassigned` 任务属于全局，多租户下需要归到具体租户。
- `events`、`workbench`、`studio-store` 都只带 `projectId`，需要能反查租户（建议：只按 projectId 查，但 projectId 必须先过归属校验，避免到处加列）。
- 创意文档的 `userId:projectId` 键与其它模块不一致，改造时要统一到项目维度（项目归属决定可见性），否则「同租户不同成员协作同一项目」会互相看不到。

### 3. 文件与媒体

- `allowedRoots()` 把**所有项目的根目录**都放进许可列表，等于任何登录用户可读任意项目文件。要改成「只允许当前用户有权限的项目目录 + 全局公共目录」。
- `/api/media/file`、`/api/media/open`、`/api/uploads` 都依赖这个许可列表，必须一起收口。
- 项目目录名是「项目名-后缀」，落在全局 `projectRoot` 下；多租户建议改成 `项目根/租户/项目`，方便整租户备份、迁移和删除。
- 智能体的 `project_files.BOUND_ROOTS` 与 `ROOT/data/workspace` 同理，需要带租户前缀，并且校验调用方对项目的权限。

### 4. 实时通道

- `/api/task-events/stream`（`server.js:1896`）把全部 `job`/`refresh` 事件推给所有连接。要按「连接所属租户 → 可见项目集合」过滤。
- 智能体的执行流（SSE）同样要带租户过滤。

### 5. 配置与密钥

- `config.json` 是所有租户共用的：模型 Key、渠道（`channels`）、`autodlKeys`、提示词映射、UI 设置全在一份里。
  多租户要拆成「平台级配置（不允许租户改）」+「租户级配置」，租户管理员只能看/改自己那份。
- **「管理器」类型渠道（`manager-video`）必须从全局配置挪到用户级配置**：每人填自己机器的地址和令牌，见第五节。
- 密钥要落库加密或至少标记敏感字段，导出/备份时脱敏。

### 6. 执行端（管理器）归属

管理器本身不用改多租户，但创作台这一侧要改三件事：

1. **渠道配置按用户存**：现在 `config.channels.video` 里那条 `manager-video`（baseUrl + apiKey，默认 `http://127.0.0.1:17778`）是全局的，多用户会互相覆盖。改成 `user.channels`。
2. **不能再由服务端拉起管理器**：`server.js:648` 会在服务器上 `spawn node src/server.js` 起管理器。共享部署下这个动作没有意义，必须禁用（仅本地模式保留）。
3. **连接方向要能跨机器**：见第五节拓扑。

下载物料的落点不变——视频仍从「该用户自己的管理器」取回，写进共享创作台的项目目录。

## 四、目标模型

```
租户 tenant
├── 成员 membership（角色：owner / admin / member）
├── 配置（模型 Key、渠道、提示词映射、UI 偏好）
└── 项目 project（多个）
    ├── 任务 / 事件 / 工作台条目
    ├── 素材 / 媒体 / 上传 / 导出
    └── 智能体工作区（会话、知识库、插件）

用户 user
└── 执行端绑定（自己的管理器：地址 / 令牌 / 平台账号，仅本人可见）
```

- **身份**：`userId` 唯一；`membership` 承载「哪个用户属于哪个租户、什么角色」。
- **数据归属**：只有 `tenantId` 是硬边界；项目内部再按 `projectId` 细分。查询永远先确定 `tenantId`，再校验 `projectId ∈ 该租户`。
- **执行归属**：豆包/Gemini 账号、配额、浏览器登录态都在**用户自己的机器**上，租户不持有账号池，也不做配额分配。
- **权限**：先按租户判可见，再按项目判可写；跨租户一律 404（不返回 403，避免探测存在性）。

### 权限矩阵（建议起点）

| 操作 | 平台管理员 | 租户 owner | 租户 admin | 成员 |
| --- | --- | --- | --- | --- |
| 创建/删除租户 | ✓ | | | |
| 管理租户成员、重置密码 | ✓ | ✓ | ✓ | |
| 租户配置 / 渠道 Key | ✓ | ✓ | ✓ | |
| 创建/删除项目 | ✓ | ✓ | ✓ | |
| 项目内创作、上传、导出 | ✓ | ✓ | ✓ | ✓（限自己有权限的项目） |
| 配置自己的管理器连接 | — | ✓（本人） | ✓（本人） | ✓（本人） |
| 查看租户用量/审计 | ✓ | ✓ | ✓ | 仅自己 |

## 五、部署拓扑：共享创作台 ↔ 每人本机的管理器

这是这次改造里唯一的新架构问题。创作台在服务器上，管理器在用户电脑上，服务器默认**够不到**用户机器的 `127.0.0.1:17778`。三种做法：

### 方案 A：同内网 / VPN 直连（改动最小）

- 管理器监听地址改为可配置（默认仍是 `127.0.0.1`），部署时绑定到内网网卡；
- 依赖 `apiToken` + 允许来源 IP 白名单（建议只放行创作台服务器）；
- 用户在「设置 → 管理器连接」里填自己机器的 `http://内网IP:17778` 和 `connection.json` 里的 token，存在 `user.channels`；
- 服务器按当前用户取对应渠道调用。

优点：管理器代码基本不动，只是把已存在的渠道配置挪到用户级、加一个监听地址选项。
缺点：要求服务器能访问到客户端机器（同网段或 VPN），端口对外开放有风险。

### 方案 B：管理器主动外联（跨公网首选）

- 管理器加一个「外联」模块：用用户令牌连到创作台的 WebSocket 通道并注册；
- 创作台把任务下发给该用户绑定的执行端，结果（视频文件）由管理器主动回传到创作台；
- 不需要公网 IP、不需要端口映射，天然按用户区分。

优点：部署最省心，安全性好（无入站端口）。
缺点：管理器要新增外联/回传逻辑，创作台要新增下发队列与断线重连，工作量比 A 大。

### 方案 C：浏览器直连本机（不推荐）

页面由服务器下发，浏览器直接请求 `http://127.0.0.1:17778`。
需要管理器放宽 Origin 校验、处理 CORS，任务执行与文件回传都要挪到浏览器侧，还要处理 HTTPS 页面的混合内容限制。改动面最大，收益最小。

**决定（2026-11-05）**：直接做方案 B（管理器主动外联）。C 不做；A 只作为临时兜底，不再作为主路径。

### 五之一、外联通道第一版（已实现）

不引入 WebSocket / 新依赖，用「长轮询 + 回传」两三个接口就够：

| 接口 | 方向 | 用途 |
| --- | --- | --- |
| `GET /api/executor/poll?token=&wait=25` | 管理器 → 创作台 | 取命令；同时当心跳，25 秒空转一次 |
| `POST /api/executor/reply?token=` | 管理器 → 创作台 | 回结果（≤1MB 内联 base64） |
| `POST /api/executor/blob?token=&id=` | 管理器 → 创作台 | 大文件（成片）单独上传，避免几十兆塞进 JSON |
| `POST /api/executor/pair` | 浏览器 | 给当前登录用户签发配对令牌 |
| `GET /api/executor/status` | 浏览器 | 通道在线状态、版本、最近错误 |
| `POST /api/executor/probe` | 浏览器 | 走通道拉一次管理器状态，验证链路 |

- 创作台侧：`src/executor-channel.js`（令牌、队列、长轮询、请求/应答、blob 落盘）、`src/executor-transport.js`（统一的 `requestJson` / `downloadBuffer`，本机直连与通道两条路同构），视频渠道里凡是 `httpJson` 的调用已全部换成它。
- 管理器侧：`src/outbound.js`（轮询、执行、回传、指数退避、代际守卫），命令只允许打到本机 `/api/*`，凭据由管理器自己补，不在通道上传输。
- 配置：管理器「系统管理 → 外联通道」填创作台地址和配对令牌；创作台「设置 → 执行端」生成令牌、看在线状态、测通道。
- 实测：小请求 31–32ms；8.2MB 成片走 blob 回传 74ms；`video-plugins` / `channels` / `manager-video` 三组测试全绿，本机直连路径未受影响。
- 已补（2026-11-05 第二轮）：同一用户可生成多条配对令牌，设置页列出、撤销，并可把任意一条设为视频任务通道；令牌仍绑定用户（用户归属租户），未额外加租户列。

### 已落地：多租户主体（阶段 1–3，2026-11-05）

**数据模型**（全部存 SQLite `data/wmd.sqlite`，不再用 JSON 文件）
- 表：`tenants` / `users`（带 tenantId + role，`isAdmin` 是平台管理员）/ `sessions` / `projects`（带 tenantId、ownerUserId）；
- 老数据自动迁移：第一次打开库时建默认租户 `tnt_default`，把现有用户和全部项目导入，原 JSON 改名 `*.imported.json`（已在本机数据上验证）；
- 配套迁移：执行端令牌、素材分类、文件别名、剧集分组也进同一个库，见 `docs/storage-review.md`。

**鉴权**
- 注册：首个用户建默认租户并成为平台管理员；之后只能由管理员创建用户，或打开 `signup.open` 让新用户各自开一个租户；
- 新增 `/api/tenants`（GET/POST/PUT/DELETE）、`/api/users`（GET/POST）、`/api/users/:id`（PATCH/DELETE）；
- 权限：平台管理员管所有租户；租户负责人/管理员只能管本租户的成员，不能动平台管理员。

**资源隔离**
- `scoped()` 现在会先做归属校验：传别人的项目 id 一律 404，不返回 403（不暴露存在性）；
- `/api/projects` 按租户过滤，项目的读/改/删、切换当前项目都要过校验；
- 任务列表、事件列表（event-store 增加 `projectIds` 白名单）、工作台（`workbench-routes` 统一过 `scope()`）都按租户过滤；
- 未归档数据（没有项目的历史任务/素材/工作台状态）只给默认租户看，其它租户各用各的桶；
- 文件访问：`allowedRoots(tenantId)` 只放行本租户项目目录，非默认租户不再能读全局的 assets/media/uploads；
- SSE 只推本租户的任务事件；
- 智能体代理强制注入校验过的 `x-project-id`，客户端伪造的会被丢弃。

**界面**：设置里新增「租户成员」页（看当前租户和成员、加人、改角色、移除；平台管理员还能建租户）。

**验收**：新增 `tests/tenant-isolation-api.test.js`，覆盖项目读写删、切换项目、任务/事件/素材列表、按路径取文件共 7 类越权，全部 4xx；`project-isolation` / `task-lifecycle` / `workbench` / `events` / `creative` / `media` / `agent-proxy` 等 85 项回归全通过。

**还没做**（后续迭代）：每用户独立的管理器渠道配置（当前是租户级选择任务通道）、邮件发送（邀请/重置用一次性链接）。每用户界面偏好、邀请/密码重置、租户级配置与模型 Key、配额（用户/项目/每日任务/存储/并发）与审计日志/导出已完成。

## 六、改造方案（按阶段，风险从低到高）

### 阶段 0：决策（不动代码）

1. **部署形态**：创作台放共享服务器，还是每人本机一套？（决定要不要做多租户）
2. **创作台 ↔ 管理器**：方案 A 还是 B？（见第五节）
3. **项目协作**：项目是否允许租户内多人共享（决定权限模型复杂度）。

### 阶段 1：数据模型与迁移

- 新增 `data/tenants.json`；`users.json` 增加 `tenantId`（或拆出 `memberships.json`）；`projects.json` 增加 `tenantId` 与 `ownerUserId`。
- 迁移脚本：现有 1 个用户 → 默认租户 `default`；现有全部项目 → 该租户；`unassigned` 任务 → 该租户。
- 目录迁移：`项目根/<租户>/<项目>`，保留旧路径兼容读取一个版本。
- 落库改 SQLite（可选但推荐）：项目、任务、事件现在的存法是一次性全量读写 JSON，多用户并发会踩坑。

### 阶段 2：认证与授权

- `auth.js` 扩展为租户感知：注册（首次=平台管理员）、邀请、登录时选定租户、会话带 `tenantId`。
- 统一中间件：解析会话 → 得到 `{userId, tenantId, role}` → 挂到 `req.ctx`；所有 `/api/*` 走这里。
- 显式开关 `auth.enabled`（配置项），默认 true；删用户文件不再等于开放。
- 改密、踢下线、登录限流。

### 阶段 3：资源隔离（核心工作量）

- `scoped()` 改为 `resolveProject(ctx, requestedId)`：查不到归属直接 404。
- `/api/projects` 按租户+成员过滤。
- `allowedRoots()` 改为按 `ctx` 计算。
- SSE 按 `ctx` 过滤；智能体的流式接口同理。
- 创意文档键从 `userId:projectId` 改为 `projectId`（+ 租户校验）。

### 阶段 4：配置分层

- `config.json` 拆平台级 / 租户级 / 用户级；渠道 Key 按租户；管理器渠道按用户；导出脱敏；提示词映射按租户覆盖。

### 阶段 5：执行端绑定

- 管理器渠道从全局挪到用户级，前端加「我的管理器」配置页（地址、令牌、连通性测试、当前账号概览）；
- 服务端按当前用户选渠道调用，替换掉 `managerChannel()` / `managerBaseUrl()` 的全局读取；
- 共享模式下禁用「服务端启动管理器」（`server.js:648`）；
- 按所选拓扑（A/B）实现连通。

### 阶段 6：智能体隔离

- 代理层强制注入可信 `X-Project-Id`（丢弃客户端值），校验租户归属；`HARNESS_AUTH_MODE` 默认 `controller`；
- 工作区目录、知识库、插件表加租户维度。

### 阶段 7：部署与加固

- 反代 + HTTPS + Cookie `Secure`；Origin/CSRF 校验改为按实际域名；限流与审计日志；备份策略按租户导出。

### 阶段 8：验收

跨租户越权用例（必须全部 404）：

1. A 租户用户带 B 的项目 id 访问 `/api/projects/:id`、任务、事件、工作台、创意文档；
2. 用 `path=` 读 B 项目下的素材/成片；
3. 连接 SSE 是否能收到 B 的事件；
4. 智能体接口伪造 `X-Project-Id`；
5. A 用户配置的管理器地址/令牌，B 用户是否可见或可复用；
6. 直接改 Cookie/令牌重放；
7. 删除 `users.json` 后接口是否仍要求登录。

## 七、硬约束

1. **创建台与执行机分离**：服务器必须能触达用户本机的管理器（方案 A 需要网络可达，方案 B 需要外联通道）。这是拓扑约束，不是代码能绕过的。
2. **本机文件路径就是数据边界**：租户隔离最终落在目录隔离上，任何「按路径取文件」的接口都是风险点。
3. **配额跟着人走**：豆包账号额度在用户自己的机器/账号上，租户看的是「谁用了多少」，不是「租户池还剩多少」。
